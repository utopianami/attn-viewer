# 사고 플레이북 라이브러리 설계 (2026-07-13)

블로그 코퍼스에서 블로거들의 사고방식·리서치 방식·정보→결론 연결 방식을 추출해
"상황별 플레이북"으로 쌓아두고, 질문이 오면 맞는 플레이북을 골라
QA 엔진(PLAN·SYNTHESIZE)이 그 절차대로 답하게 한다.

1차 영역 = 메모리/반도체 (사용자 확정).

## 핵심 관점 (브레인스토밍 합의)

- **패턴이 1급 단위, 블로거는 출처.** 한 블로거도 주제마다 사고가 다르고,
  다른 블로거가 같은 패턴을 쓸 수 있다. 여러 블로거가 공유하는 패턴 = 교차 검증된 패턴.
- **질문마다 맞는 사고방식을 채택한다.** 블로거 카피가 아니라 상황 매칭.
- 카피 대상은 출처 목록이 아니라 **확인 절차와 연결 논리** —
  엔진이 가진 도구(네이버 뉴스·가격·toss)로 같은 절차를 수행한다.

## 선행 연구 근거 (2026-07-13 검색 검증)

- **ReasoningBank** (Google 2025, arXiv 2509.25140): 전략 항목 저장소 + 유사도 검색 주입. 뼈대 동일.
- **Buffer of Thoughts** (arXiv 2406.04271): 문제 유형별 사고 템플릿 선택.
- **Agent Workflow Memory** (arXiv 2409.07429): 절차 라이브러리 → 절차 지침 주입.
- **InvestPhilBench** (arXiv 2606.25984): 투자 대가 사고를 카드 2층(원칙 카드 + 프레임워크 카드)으로
  구조화. 프레임워크 = 순서 있는 게이트 + 킬 조건. LLM 실패 6유형(킬 조건 누락·시점 뭉개기·
  조작적 정의 뭉개기·게이트 날조·목소리 섞임·시대착오 적용). 답변 전체 점수는 포화되어
  절차 결함을 숨김 → 게이트 단위 채점(GRA) 필요. 카드 전체 주입은 역효과 → 관련 카드만.
- **Thinking Machines** (전문가 판단 복제): 정적 프롬프트만으로 47→78%.
  모델-라벨 어긋남 사례만 전문가 라우팅으로 검수 집중.

우리와의 차이: 위 연구 대부분은 에이전트 자신의 경험에서 증류. 우리는 **사람 전문가 글에서 채굴**
→ "글에 적힌 사고를 충실히 추출했는가"가 고유 품질 문제 (원문 인용 강제 + holdout으로 대응).

## 저장 구조 — 카드 2층

```
사고 카드 (글 단위)                          플레이북 카드 (상황 단위)
storage/users/<user>/corpus/naver/          storage/users/<user>/corpus/
  <blogId>/analysis/<articleId>.json    →     playbooks/<slug>.json
글 하나의 사고, 원문 인용 필수                여러 사고 카드를 게이트 구조로 합성
```

### 사고 카드 스키마 (글 단위 추출)

```json
{
  "id": "naver-ranto28-XXXX",
  "situation": "어떤 상황/질문에 대한 사고인가 (플레이북 매칭 인덱스)",
  "checks": [
    { "order": 1, "what": "뭘 확인했나", "why": "왜 이걸 봤나",
      "kill": "저자가 '이러면 아니다'라고 한 조건 (없으면 null)",
      "quote": "원문 인용 (필수 — 못 대면 필드 비움)" }
  ],
  "connection": { "logic": "확인한 것 → 결론 연결 방식", "quote": "원문 인용" },
  "reservations": { "text": "유보 지점·생각 바꾸는 조건", "quote": "원문 인용" },
  "conclusionType": "방향 판단 | 종목 비교 | 시점 판단 | ...",
  "topics": ["HBM", "감산"],
  "publishedAt": "글 게시일 (asOf 계산용)",
  "extractedAt": "ISO", "model": "...", "sourceContentHash": "sha256"
}
```

규칙: **모든 필드에 원문 인용 필수, 인용 못 대면 빈칸.** 일반론·구조 날조 차단.
튜닝 기준: "이 카드만 보고 어느 블로거·어떤 글인지 특정할 수 있는가" — 일반론 추출물 탈락.

### 플레이북 카드 스키마 (합성)

```json
{
  "slug": "memory-cycle-direction",
  "situation": "메모리 사이클 방향 판단",
  "triggers": ["감산·증산 발표", "재고 지표", "HBM 계약 뉴스"],
  "gates": [
    { "order": 1, "check": "무엇을 확인", "why": "왜 이걸 먼저",
      "kill": "어떤 값이면 시나리오 기각/중단 (없으면 null)",
      "operationalization": "그 블로거의 구체 기준 — 숫자·조건 보존",
      "evidence": ["naver-ranto28-XXXX", "naver-crush212121-YYYY"] }
  ],
  "connection": "게이트 결과 → 결론 연결 방식",
  "reservations": "유보 조건",
  "asOf": "이 사고가 유효한 시기 (생각이 바뀌면 새 버전 카드, 덮어쓰지 않음)",
  "sources": { "bloggers": ["ranto28", "crush212121"], "articleCount": 9 },
  "status": "draft | holdout_passed"
}
```

- 게이트는 확인 목록이 아니라 **순서 + 킬 조건** (InvestPhilBench의 핵심).
- 1명만 쓰는 패턴은 근거 글 3편 이상일 때만 카드화.
- 항목마다 근거 사고 카드 링크 = 감사 가능성.

## 추출 퍼널 (글이 많은 문제의 답)

전체 ~6,600편을 다 추출하지 않는다. 3단 퍼널:

```
① 키워드 필터 (무료, grep)         : ~6,600 → 508편 (2026-07-13 실측)
   HBM|하이닉스|마이크론|Micron|D램|DRAM|낸드|NAND|디램|파운드리|메모리 반도체
   블로그별: ranto28 125 · jakojako 138 · tosoha1 63 · crush212121 60 ·
   cybermw 56 · yminsong 22 · 기타 44
② 경량 LLM 분류 (저렴)             : 508 → 예상 150~250편
   "반도체가 글의 주제인가(스침 제외)" + "추론글인가" 동시 판정
③ 상위 모델 4층 추출 (비쌈)         : 최종 그룹만, 최신→과거 순
```

- 배치 실행은 crawler·summaries와 같은 패턴: `analysis/<id>.json` 존재 시 스킵(재개 가능),
  `sourceContentHash`로 재추출 감지, jobs 로그, 요청 간격.
- **튜닝 먼저**: ③은 최신 20~30편으로 시작, 눈 검증으로 프롬프트 확정 후에만 배치 확대.
- ②의 분류 정확도는 배치 전 연도별 표본으로 점검 (옛 글 문체 차이 오분류 대비).
- 모델명·단가는 구현 시점에 검색으로 확정 (스펙에 박지 않음).

## 검수 — 어긋남 라우팅

전수 눈 검사 대신 의심 사례만 사용자 확인 대상으로 올린다 (블로거 탭에 표시):
- 인용을 못 단 필드가 있는 카드
- 기존 summaries 요약과 situation/결론이 어긋나는 카드
- 튜닝 구간(첫 20~30편)은 전수 확인

## 합성 (사고 카드 → 플레이북)

- 블로거 경계 없이 situation·topics가 비슷한 사고 카드끼리 묶는다.
- 초기 물량(수십 편)은 LLM이 전체를 보고 패턴 후보 제안 → 사람이 확정.
- 평균화(별자리 운세화) 방지: 게이트마다 근거 카드 링크 필수, 카드당 게이트 수 상한(예: 7),
  구체 숫자·조건(operationalization) 없는 게이트는 채택 보류.
- 시점 관리: 같은 상황이라도 시기별 사고가 다르면 asOf 버전을 나눈다.

## 선택 + 주입

- 질문 도착 → 기존 triage(질문 종류 분류) 결과 + 테마 매칭으로 플레이북 선택.
  매칭 없으면 주입 없음 = 현행 동작 그대로 (안전 기본값).
- **관련 플레이북 1장만** 주입, 길이 상한. (전체 주입은 역효과 — InvestPhilBench 실증)
- 분배: PLAN에는 게이트(확인 절차·킬 조건), SYNTHESIZE에는 connection·유보 기준.
- 경계 명시: **절차로만 쓰고 사실로 쓰지 않는다** — 플레이북 내용을 답변의 근거 사실로
  인용하지 않도록 프롬프트에 못 박음 (문체 흉내·출처 혼동 방지).
- holdout 통과(status=holdout_passed) 카드만 주입 대상.

## 검증

1. **holdout (게이트 단위 채점)**: 최근 반도체 글 몇 편을 추출에서 제외하고,
   그 글의 상황만 주고 플레이북으로 "뭘 어떤 순서로 확인할지" 예측 →
   실제 글의 게이트 순서·킬 조건과 **게이트 단위로** 대조. 답변 전체 인상 점수는 쓰지 않는다
   (포화되어 절차 결함을 숨김). 대조군 = 플레이북 없이 예측.
2. **A/B**: `engine/evals/` 골든셋에 반도체 전망·판단형 질문 보강, 주입 전후 비교.
   지표도 절차 재현 중심 + 기존 코드 지표.

## 오류 처리

- 추출 실패 글: 스킵 + jobs 로그 기록, 같은 사유 반복이면 정책이 아니라 버그로 취급.
- 플레이북 파일 손상/스키마 불일치: 해당 카드만 무시하고 로그, 주입 없이 정상 답변.
- 주입 후 답변 품질 하락이 A/B에서 확인되면: 주입 게이트(status) 되돌림으로 즉시 차단 가능.

## 실행 순서

1. 추출 스크립트 + 사고 카드 스키마 + 퍼널 ①② (키워드는 실측 완료)
2. 최신 20~30편 추출 → 블로거 탭 검수 UI(글 옆 카드 표시) → 프롬프트 튜닝
3. 최종 그룹(150~250편) 배치 추출 (holdout용 최근 글 제외)
4. 플레이북 합성 (LLM 제안 + 사람 확정) → holdout 검증
5. triage 매칭 + PLAN·SYNTHESIZE 주입 + A/B

## 모델 배치 (사용자 확정 2026-07-13: 기본값 codex CLI, $0)

- 퍼널 ② 분류 + ③ 추출: **codex CLI** (구독, API 키 불필요) — summaries.mjs의
  "마지막 메시지를 파일로 받아 파싱" 패턴 재사용. 추출은 CLI에서 가용한 최상위 모델로.
- **인용 충실도는 코드로 검증**: 사고 카드의 모든 quote가 원문 Markdown에 실제
  부분 문자열로 존재하는지 대조 (정규화 후). 실패 필드는 비우고 카드에 플래그 —
  인용 날조·변형을 LLM 심판 없이 잡는다.
- **API 전환 조건**: 튜닝 20~30편에서 인용 충실도·킬 조건 포착이 기준 미달일 때만
  추출 역할을 API(Opus 4.8 $5/$25, 250편 ≈ $17)로 올린다. 가격이 아니라 측정으로 결정.
  (단가 2026-07-13 검색 검증: Opus 4.8 $5/$25 · Sonnet 4.6 $3/$15 · Haiku 4.5 $1/$5)
- 합성·holdout 심판: 호출 수가 적으므로 동일 원칙 — CLI 기본, 미달 시 API.

## 미확정

- 플레이북 매칭 키의 세부(질문 유형만 vs 테마·종목까지) — 2단계에서 실제 카드를 보고 결정.
- holdout 채점의 LLM 심판 프롬프트 — 4단계에서 설계.
