> 다른 세션에서 이어서 작업하기 위한 핸드오프 문서.
> 이 대화에서 확정된 설계와 미결 사항을 담는다. 구현은 아직 시작하지 않았다.

## 목적

**"지수 숏 + 지수대비 아웃퍼폼 종목 롱" 전략이 되는지 검증하는 연구 도구.**
- 거래 집행은 범위 밖 (되는 게 확인되면 그때 별도로 붙인다)
- 대상: 국내 주식, 일간~주간 리밸런스, 벤치마크는 코스피 지수
- 재료: TabPFN(크로스섹션 피처→아웃퍼폼 확률), Kronos(일봉 시퀀스→수익률 예측),
  토스 API(데이터 소스 — 아래 참고 문서)

## 확정된 구조 — 3층, "데이터 경로엔 LLM 없음"

```
[1층: Tool 4개 — 순수 Python CLI, LLM 무관]
  toss_data      일봉·수급·재무 수집 → parquet 누적
  kronos_score   종목별 일봉 → n일 수익률 예측 점수
  tabpfn_score   크로스섹션 피처 → 지수대비 아웃퍼폼 확률
  backtest       시그널 파일 → 지수숏+롱바스켓 P&L (비용 포함)

[2층: 전략 루프 — cron, 결정론적]
  매일 장마감 후: 수집 → 두 모델 점수 → 랭킹 → 시그널 파일 동결
  → 페이퍼 포트폴리오 업데이트
  시그널 파일 = 날짜 + 모델버전 + 설정해시 + 종목·비중 (전부 재현 가능)

[3층: 실험 관리자 — LLM 운전자, 교체 가능한 부품]
  결과 해석·이상 감지·실험 큐 관리·연구 노트 작성
  v1 = 클로드 세션, v2(필요시) = PydanticAI + 로컬 모델
```

핵심 원칙: **픽(종목 선정)은 코드가, LLM은 실험 관리만.** 픽 경로에 LLM이 있으면
같은 입력에 다른 출력이 나와 전략 검증 자체가 불가능해진다. LLM으로 시그널을
합성하고 싶어지면 "LLM 출력을 그날 시그널 파일로 동결"하는 방식으로만 —
포워드 검증은 가능, 과거 백테스트는 불가함을 감수.

## 운전자 문제의 결론 (대화의 핵심 갈등과 해소)

- 처음 아이디어: 로컬 모델 + 클로드/코덱스 호출 툴 + TabPFN/Kronos/토스 툴
  (클로드로 오토리서치 돌리면 자유도는 좋은데 24시간 돌리기엔 비싸서)
- 해소: 무거운 일은 전부 1~2층 코드가 하므로 **LLM 틱은 하루 1~2회, 회당 몇 분**
  수준으로 얇아진다. 그래서:
  1. **v1: 클로드 세션이 운전자.** 구축 비용 사실상 0 (CLAUDE.md 역할 정의 + cron).
  2. **일주일 돌리며 틱당 토큰 실측.**
  3. **비싸다고 판명되면 그때** PydanticAI + Qwen3 32B(Q4, Ollama)로 교체.
     상태 파일 규약이 같아서 교체 비용 작음.
- 만드는 과정 자체는 어차피 클로드/코덱스가 코드 짜는 일회성 구축 비용 —
  운영 비용과 별개.

## 상주 프로세스 없음 — 파일로 이어달리기

프로젝트 폴더 하나가 전부:

```
quant-lab/
  pipeline/     수집·Kronos·TabPFN·백테스트 코드
  data/         누적 일봉·수급 (parquet)
  signals/      매일 하나씩 생기는 시그널 파일
  results.db    실험·성과 기록 (DuckDB)
  research.md   연구 노트
  queue.yaml    실험 대기열
  CLAUDE.md     운전자 역할 정의
```

하루 흐름 (v1):
- 16:00 cron → `python -m pipeline.daily`: 데이터 수집 → 점수 → `signals/YYYY-MM-DD.json`
  생성 → 어제 시그널의 실측 성과를 results.db에 기록. LLM 없음.
- 16:30 cron → `claude -p "오늘 틱 처리해"`: results.db 읽고 research.md에 한 줄 기록,
  queue.yaml의 대기 실험을 내일 설정에 반영. 몇 분 후 종료.
- 아무 때나 사용자 → 폴더에서 `claude` 대화: 노트·결과 읽고 답변, 새 연구주제를
  queue.yaml에 추가. ("연구주제 유연하게 넣기" = 이 대화가 실험 config로 착지하는 것.
  config로 표현 안 되는 주제만 코드 수정 → codex 에스컬레이션)

chat와 tick은 **같은 툴셋·같은 상태 파일, 시동 거는 주체만 다름**. 동시성은
"queue는 append만, tick은 시작 시점 스냅샷 처리" + 락파일 하나로 충분.

## 에스컬레이션 규칙 (명시적으로 박는다)

- 코드 수정 필요 → codex
- 같은 실험 2회 연속 실패, 또는 지표가 정의된 범위 밖 → claude 해석 요청
- 주간 1회 연구 리뷰(방향 재검토) → claude
- 그 외 호출 금지 — 대신 research.md에 질문 남기고 사용자가 chat으로 들어왔을 때 확인

## 검증 방식 — 포워드 중심

- 토스 차트는 회당 200~300봉이라 히스토리 약 1년치부터 시작 (누적 수집으로 성장)
  → 백테스트는 sanity check 용도만
- 본 검증: **매일 시그널 동결 → 다음날부터 실측 수익률 추적** (포워드 페이퍼)
- 성공 기준은 시작 전에 숫자로 확정할 것 (미결 — 아래): 비용 후 지수대비 초과수익,
  히트율, 최대낙폭 등
